# @monark/app-docs

The documentation site for [monark-community/app](https://github.com/monark-community/app). A Next.js
static export: file navigation on the left, the article in the middle, "On this page" on the right,
and ⌘K search across every page title.

```bash
pnpm install
pnpm sync:docs --source ../app   # pull the app repo's Markdown in
pnpm dev                         # http://localhost:3000
```

## Where this came from

The shell is a fork of [`@sntlr/registry-shell`](https://github.com/scintillar-com/registry-shell) —
the same viewer that renders [Monark UI](https://ui.monark.io)'s documentation — trimmed to
docs-only and re-pointed at a nested content tree. Files under `components/`, `hooks/` and
`lib/` are largely upstream code and are deliberately kept diff-able against it: the `@shell/*`
import alias is the shell's own convention, retained so upstream fixes can be read across
without a rename pass.

What changed in the fork:

| Upstream | Here |
| --- | --- |
| Components / blocks / docs sections | Docs only ; the header tabs are **docs sections** instead |
| Flat `content/docs/*.mdx` | Nested `content/docs/<section>/[<group>/]<name>.mdx` |
| Config read via CLI env vars | [`docs.config.ts`](./docs.config.ts) imported directly |
| Homepage lists components | Homepage lists sections |
| Preview / registry / a11y / props surfaces | Removed |

## Layout

```
docs.config.ts          ← branding + section list (the white-label surface)
styles/theme.css        ← design tokens + fonts (imported last, wins the cascade)
content/docs/           ← generated by `pnpm sync:docs` ; committed
  user-guide/
  modules/
  technical-documentation/
app/(shell)/            ← root layout, homepage, /docs/[...slug]
components/             ← header, sidebar, TOC, search, MDX renderer, shell-ui primitives
lib/                    ← config resolution, docs loader, i18n, branding
scripts/                ← sync-docs, generate-search-index
```

## Content

`content/docs/` is **generated** — every file carries a `source:` field in its frontmatter
pointing back at the Markdown it came from. Edit the prose in `monark-community/app` and re-run
the sync; don't edit the MDX here.

Figures work the same way: `pnpm sync:docs` copies the source repo's `docs/assets/` into
`public/docs-assets/` and rewrites the image links to point there. Both the MDX and the images
are **committed**, so the site builds from a clean checkout without the source repo present —
`pnpm build` does not run the sync, so anything the committed content references has to be
committed alongside it.

`pnpm sync:docs` maps the source repo like this:

| Source | Section |
| --- | --- |
| `docs/user-guide/*.md` | `user-guide` |
| `packages/*/docs/user-guide.md` | `modules` |
| `docs/technical-documentation/*.md` | `technical-documentation` |

Along the way it derives frontmatter (`title` from the first H1, `description` from the opening
paragraph, `order` from the section's `_index.md` when there is one), rewrites repo-relative `.md`
links to site routes, and escapes the characters MDX would read as JSX or expressions. A link into
content the site doesn't publish becomes an absolute GitHub URL rather than a dead link.

A file named `_index.md` is its folder's landing page: `user-guide/_index.mdx` answers at
`/docs/user-guide`.

## Ordering

The sidebar is not alphabetical. Order is resolved per directory, over that directory's pages
**and** the folders under it together, so a folder can sit between two pages rather than always
after them. Three levers, in priority order:

1. **`order:` in a source page's frontmatter.** The blunt instrument, for when a page has to sit
   somewhere specific regardless of anything else.
2. **The contents list in the folder's `_index.md`.** The links there, in the order they appear,
   *are* the running order. This is the usual lever: the list already says what a reader should
   meet first, so reordering the list reorders the sidebar. A link to a section that has since
   become a folder (`webhooks/_index.md`) still names that folder.
3. **Alphabetical**, for anything neither of the above mentions, after the section's `pinned`
   entries from `scripts/sync-docs.ts`.

A folder's own position comes from its **parent's** ordering, carried on its `_index`. Reading it
from the landing page's order *within* its own folder is always 0, which silently sorts every
folder first.

## White-labeling

Three files, no component edits:

1. **[`docs.config.ts`](./docs.config.ts)** — site name, description, canonical URL, GitHub link,
   favicons, and the section list (each section's directory, label, and sidebar icon).
2. **[`styles/theme.css`](./styles/theme.css)** — fonts and design tokens. Imported at the very end
   of `app/globals.css`, so `:root` / `.dark` overrides win the cascade against the shell's defaults.
3. **`public/`** — `favicon.ico`, `favicon_dark.svg`, `favicon_light.svg`, and an OG image if you
   reference one.

Adding a section is a directory under `content/docs/` plus an entry in `sections`. An undeclared
directory still renders (title-cased, sorted last), so content is never invisible just because the
config wasn't updated.

## Commands

| Command | What it does |
| --- | --- |
| `pnpm dev` | Dev server on `localhost:3000` |
| `pnpm build` | Static export → `out/` |
| `pnpm start` | Serve the built `out/` locally |
| `pnpm sync:docs [--source ../app] [--clean]` | Pull the source repo's Markdown into `content/docs/` |
| `pnpm generate:search-index` | Rebuild `public/api/search-index.json` (runs automatically before dev/build) |
| `pnpm typecheck` / `pnpm lint` | The usual |

## Deploying

`pnpm build` produces a pure static tree under `out/` — no server runtime. Deploy it to Vercel
(auto-detected), Netlify (`publish = "out"`), GitHub Pages, or any static host.
